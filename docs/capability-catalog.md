# BCM4378 discovery catalog

The research device is a 2020 M1 MacBook Air (A2337, `MacBookAir10,1`) with a Broadcom BCM4378. The latest read-only check found macOS 27.2.1 build 26B131, Wi-Fi firmware `18.20.511.0.7.8.207` with FWID `01-2606388a`, and active `en0` on the default route. Its firmware capability reply repeated the same 90 words in the saved order. This catalog covers the findings recorded through [PR #34](https://github.com/bnelabs/bcm4378-research/pull/34). [Device identification](findings.md), [Firmware snapshot](../evidence/2026-11-17-live-firmware-capabilities.json)

The [firmware feature index](firmware-feature-index.md) lists every word observed in the live legacy reply or found in the mapped driver word table, plus every direct bit update in the extended parser. The notes below explain the processes behind those names and the measurements that make them useful.

[Firmware and board selection](firmware-layout.md#files-requested-by-the-running-driver) |
| Installed Wi-Fi builds | The 35 executable names collapse to three distinct payloads. Honshu B1, Capri B1 and Kyushu B3 share the version string and carry distinct firmware IDs. The aliases record board, antenna profile and radio module choices. [Installed package and build identities](firmware-layout.md#installed-package) |
| Signing and verification path | Both Apple driver slices passed strict signature verification. The stock BCM4378 Hashstore package declares a matching loader personality. | Board calibration and regulation | There are 250 Wi-Fi NVRAM paths covering ten distinct text payloads. Each declares two-bit chain masks. The country/channel rules file (CLM) and transmitter caps file (TxCap) are separate. Their 35 names each collapse to seven validated payloads. TxCap bodies fall into four groups. | NVRAM text handling | macOS preserves a space before the equals sign in a slice-specific power threshold assignment. The pinned Linux parser drops that assignment in the offline replay. The saved vendor text produces 296 modeled macOS records and 295 retained Linux assignments. All three images call a helper with the threshold names. The actual threshold that firmware applies remains open. [macOS normalization](macos-nvram-normalization.md), [Linux boot-text replay](ram-diagnostics.md#stock-text-and-linux-boot-serialization) |
| Image boot and overlay candidates | The Linux reference loader treats the executable as a flat image. All three images have repeated branch-like openings and a likely ROM replacement table. The two B1 tables have 768 rows each and B3 has 374. The model explains how installed bytes could override ROM routines. Runtime placement and execution remain open. [Loading, comparison, and overlay trace](firmware-layout.md#reference-loading-model) |
| Embedded operating system | All three shipped executables contain a decoded initialization call that prints ThreadX 5.6. [RTOS, binary paths, and instructions](rtos-threadx.md) |
| Created-thread list | Two named startup tasks share a helper in each image. A watchdog path follows the created-thread link from a build-specific head slot. The reader walks captured records for the three known stock digests. Tests used synthetic main-RAM captures. [Main and idle tasks](rtos-threadx.md#main-and-idle-tasks-in-the-stock-images) |
| Wi-Fi MAC microcode | The ARM loader selects one of two 88 KiB programs by D11 unit and copies it through the selected core's program-memory port. All three stock files contain the same two programs. Use their hashes to compare builds or verify a retained D11 readback. Live contents and the microcode instruction semantics remain open. [Core selection and destination](firmware-layout.md#d11-microcode-and-core-selection), [Readback comparison](ram-diagnostics.md#compare-a-d11-program-capture) |
| Register and memory geometry | The signed driver declares 1,892,352 bytes of ARM RAM, nine core descriptors and seventeen wrapper descriptors. The live PCIe service publishes 64 KiB and 8 MiB mapped apertures. These sizes and windows guide interpretation of retained diagnostics. Actual register values, RAM banks, and live memory contents remain unmeasured. [Memory and backplane map](chip-memory-map.md) |
| Firmware diagnostic capture | The Apple driver has a normal RAM fault attachment. Pinned Linux and Asahi register a driver-owned RAM coredump path whose copied range excludes the reported save/restore area. The repo compares a retained file against a stock image and checks capture framing. External management is needed for live tests that can reset or delay the radio. [Capture boundaries and offline comparison](ram-diagnostics.md) |
| WLAN serial metadata | I/O Registry links `wlan-debug` to the M1 UART2 service. The named service and its device metadata are recorded. Firmware console output and active access are unverified. [Serial evidence](live-access.md#wlan-serial-metadata) |
| PCIe link and low-power states | The sampled endpoints report 5 GT/s ×1 and the shared port reports 2.5 GT/s ×1. Repeated paired reads reproduced the discrepancy. L1, clock power management, latency tolerance and function-0 L1 substates appear in the published capabilities. Actual negotiated speed and state residency need separate evidence. [PCIe property and power trace](pcie-link-properties.md) |
| Host queues and firmware rings | The five roles expose FQ-CoDel queue data. Shikoku supplies 768 ordinary transmit entries, 512 receive ring entries and a 512-entry low-latency transmit sizing input. These values feed different host or firmware-facing queues. The pinned Linux trees use distinct receive ring depths and protocol-version-dependent record sizes. [Queue and ring comparison](pcie-queue-sizing.md) |

## Highest-value bench tests

1. **Peer traffic while the Mac stays online.** On an independently managed A2337 and an owned Apple peer, compare a local app transfer with an infrastructure transfer while the test Mac carries internet traffic. Record both host interfaces and use an independent receiver to see whether the bands overlap in airtime. Use the archive recovery probe to measure preview deadlines and verified archive progress during a router handoff. [Recovery probe](practical-radio-applications.md#resume-work-after-a-radio-fault), [Peer latency comparison](hp2p-low-latency.md#supported-app-control-and-a-bench-comparison), [Dual-band policy](simultaneous-dual-band.md)
2. **Separate coverage, congestion and computer-side lag.** Use the link diary during controlled obstruction or AP placement changes. Record application delay and receiver observations alongside the diary. Interpret host completion histograms, waveform timing and actual RF power using their own reference points.
